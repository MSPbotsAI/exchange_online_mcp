## PRD-20394 · 2026-10-13

- Added `exo_add_distribution_group_member` (`:49-134` @ `c0d53ea`, work branch `dev01.mbagent/PRD-20394`, not yet merged to `main` at the time of writing — this repo has no `int` branch, so re-check this path:line once merged). Mirrors `exo_remove_distribution_group_member`'s parameter shape per the ticket's explicit request.
- **Idempotency is achieved by a precondition membership read (`Get-DistributionGroupMember`), not by parsing `Add-DistributionGroupMember`'s own error text.** This was a deliberate choice over the cheaper error-text-parsing alternative: no confirmed wording exists anywhere for Exchange's "member already exists" error for this cmdlet (see `docs/tickets/PRD-20394.md` § Tech design, Option analysis — two of the three restricted-group-type error texts are equally unconfirmed, which is the same reason those are also precondition-checked rather than guessed from error text). If a future ticket on a real tenant confirms the actual wording, the precondition read could be dropped in favor of catching the error directly — but do not make that change without that confirmation; it would reintroduce exactly the risk this design avoided.
- **Group-type restriction is classified via `classify_group_restriction()`** (`src/exo_mcp/tools/_common.py`, pure function, no transport dependency) using `Get-Recipient`'s `RecipientTypeDetails`/`IsDirSynced` fields, checked in this order: on-premises-sync first (most specific signal), then dynamic distribution group, then Microsoft 365 Group (`GroupMailbox`). The order matters because a synced object can still carry an ordinary-looking `RecipientTypeDetails`.
- **There is a known, accepted TOCTOU race**: between the membership-read precheck and the `Add-DistributionGroupMember` write, two concurrent callers adding the same member could both pass the precheck. `_is_already_member()` (`:32-43`) and the fallback at `:126-131` (matching `_DUPLICATE_MEMBER_MARKERS` against the write call's own error, best-effort, not primary) cover the common case but are **not guaranteed** to catch every real-tenant wording — see `docs/tickets/PRD-20394.md` § Tech design, Non-functional (idempotency & concurrency). An unmatched race surfaces as a plain `upstream_error`, not as `already_member`. This is accepted for an admin/automation tool, not a high-QPS path.
- **Membership matching is case-insensitive** and checks `Name`/`PrimarySmtpAddress`/`Alias`/`Guid` (`_MEMBER_FIELDS`, `:14-19`) — any one matching the supplied `member` string counts as already-a-member.
- Tests: `tests/test_groups_add_member.py`, one per AC (TC-EXO-001 through TC-EXO-008) plus two extra: case-insensitive matching, and the three restricted-type error codes being pairwise distinct.
