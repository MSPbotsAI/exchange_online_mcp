# Module: `src/exo_mcp/tools/permissions.py` (mailbox/recipient permission grants)

First entry in this module doc (no prior accumulated facts existed in this repo for this file).

## PRD-20480 · 2026-10-14

- New tool `exo_add_sendonbehalf_permission` (`src/exo_mcp/tools/permissions.py` @ `3ec7afb`), placed right after `exo_add_mailbox_permission`. Additive `Set-Mailbox -GrantSendOnBehalfTo @{Add=[delegate]}` — a different right and a different cmdlet from `exo_add_mailbox_permission`'s `Add-MailboxPermission`/FullAccess: SendOnBehalf shows mail as sent "on behalf of" the mailbox rather than granting full access to it. Existing delegates are left in place (additive, not a replace). Same `verified: false` + replication-delay note pattern as the `Set-Mailbox`-based tools in `mailbox.py`.
- This is this module's first tool to use a multi-valued `{"Add": [...]}` cmdlet parameter — every prior tool in this file (`exo_add_mailbox_permission`, `exo_add_recipient_permission`, and their `Remove-*` counterparts) sets a fixed scalar `AccessRights` value. Not yet exercised against the real EXO REST endpoint (same open question as `exo_add_email_alias` in `mailbox.py`, tracked as TC-EXO-004); the documented fallback if rejected is read-merge-write via `exo_get_mailbox` + full-list `Set-Mailbox`.
- No new Exchange role needed — `Recipient Management` (this repo's existing single required role, per README) already covers `Set-Mailbox`, so this tool has no cross-repo scope-grant dependency, unlike `ms-graph-mcp`'s `graph_create_tap`/`graph_add_group_owner` half of the same ticket.
- Test coverage: `tests/test_tool_calls.py::test_add_sendonbehalf_permission_grants_delegate`, `::test_add_sendonbehalf_permission_not_found` (both added in this ticket, both passing at `3ec7afb`).
- Not covered by automated tests (needs a real tenant — see `docs/tickets/PRD-20480.md` § Self-test, TC-EXO-001b): whether a real EXO tenant's `GrantSendOnBehalfTo` actually no-ops a duplicate `Add` (additive-idempotent assumption, not yet confirmed) and whether `exo_get_mailbox` shows the delegate after replication.

## PRD-20480-r2 · 2026-10-19 (supersedes the PRD-20480 entry above)

- Real-tenant INT testing (comment `90170264109063`, Minnie Zhou, 2026-10-19) answered the open question the entry above flagged: the `{"Add": [...]}` wire shape **is rejected** by the real EXO REST endpoint with `invalid_argument "Invalid Operation"`. `exo_add_sendonbehalf_permission` (`src/exo_mcp/tools/permissions.py` @ `a43db49`) now uses the documented fallback: `Get-Mailbox` reads the current `GrantSendOnBehalfTo`, `Get-Recipient` validates `delegate` resolves to a real recipient (rejects with `invalid_argument` if not), a case-insensitive already-present check skips the write entirely if the delegate is already on the list, otherwise the full merged list is written with one `Set-Mailbox`, then a follow-up `Get-Mailbox` sets `verified`.
- The response shape changed: a `result: "added"|"already_present"` field was added rather than relying on a bare `granted: true` as the only signal — the pre-fix shape reported `granted: true` even on the call that was actually failing on a real tenant, which is why Minnie's comment caught it as a FAIL rather than a result-shape nuance.
- Imports `_read_mailbox` from `mailbox.py` rather than duplicating a second `Get-Mailbox`-projecting helper — this is the first cross-file import between these two tool modules in this repo.
- Test coverage: `tests/test_tool_calls.py::test_add_sendonbehalf_permission_grants_delegate` was rewritten for the new call sequence (same judgement, different mocked cmdlets); `::test_add_sendonbehalf_permission_not_found` now triggers on `Get-Mailbox` instead of `Set-Mailbox` (D1 reads before it writes); new: `::test_add_sendonbehalf_permission_already_present_skips_write`, `::test_add_sendonbehalf_permission_rejects_delegate_that_does_not_exist`, `::test_add_sendonbehalf_permission_merges_into_existing_list`.
- Still not covered by automated tests (needs a real tenant — see `docs/tickets/PRD-20480-r2.md` § Self-test, TC-EXO-013): whether the new read-merge-write fallback itself round-trips correctly on a live tenant, and whether `2qmxyw`'s lack of a shared mailbox (noted in the comment) affects the retest. Not fabricated as passing.
