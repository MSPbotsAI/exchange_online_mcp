# Module: `src/exo_mcp/tools/mailbox.py` (mailbox read/write/hidden-state)

First entry in this module doc (no prior accumulated facts existed in this repo before PRD-20321).

## PRD-20321 · 2026-10-12

- `exo_set_mailbox_hidden` (`src/exo_mcp/tools/mailbox.py:174-230` @ `fedf853`) used to write `HiddenFromAddressListsEnabled` via `Set-Mailbox`, then immediately call `Get-Mailbox` exactly once and return whatever that single read showed — with no delay and no retry. EXO recipient-directory changes (including this property) are well known to not always be visible to an immediately-following directory read, and this codebase had no handling for that lag. Before this ticket, a caller that hit the lag would get back a stale `false`/`true` that read as authoritative, with no way to tell it apart from a genuine failure.
- The fix is a new helper `_read_mailbox_until_hidden_matches` (`:61-90` @ `fedf853`): up to `_HIDDEN_VERIFY_ATTEMPTS` (currently 4) re-reads with `_HIDDEN_VERIFY_BACKOFF_S` (currently 0.2s) backoff between them, stopping as soon as the readback matches the requested state. If the budget is exhausted without a match, the response gains `verified: false`, `attempts`, and a `note` pointing the caller at `exo_get_mailbox` for a later re-check — it does not present the stale value as if it were confirmed.
- **The retry budget (4 attempts / 0.2s backoff) is a placeholder, not a measured value.** No real-tenant propagation-lag measurement has been done (see `docs/tickets/PRD-20321.md` on the `mcp-service-gateway` repo, § Handoff). If this ever needs tuning, these are the two constants to change, right above `_read_mailbox_until_hidden_matches`.
- The response shape is backward-compatible: on the matched path (the common case), the response is identical to before this ticket — no new keys appear. `verified`/`attempts`/`note` only appear when the retry budget was exhausted.
- Test coverage: `tests/test_tool_calls.py::test_set_mailbox_hidden_confirms_on_first_readback`, `::test_set_mailbox_hidden_retries_until_readback_matches`, `::test_set_mailbox_hidden_reports_unverified_after_retry_budget`, `::test_set_mailbox_hidden_reports_not_found` (regression guard — write-step failure on a nonexistent identity is unaffected by the new read loop). The existing `test_set_mailbox_hidden_reports_the_read_back_value` was left unmodified and still passes.
- A reusable test pattern was added for this: `_FlipAfterNReads` (local to `tests/test_tool_calls.py`, not in `conftest.py`) — a `dict.get()` stand-in that lets a test simulate a cmdlet's response changing across repeated calls within one test, which the shared `Upstream` fixture does not support (it only holds one fixed response per cmdlet for the whole test). Any future test needing a "stale-then-correct" or similar multi-read sequence against this mock should reuse this pattern rather than extending `conftest.py`'s `Upstream` (that would affect every other test in the suite).

## PRD-20321 follow-up · 2026-10-13 (supersedes the retry loop above)

- Real-tenant test showed the retry loop gave false confirmation: the read inside the same tool call landed on the server that took the write and matched on the first attempt, while an independent `exo_get_mailbox` still returned the old value 60+ seconds later. The same lag appeared in both directions (hide and unhide), and the value converged after a few minutes. So it is directory replication lag, not a failed write.
- `exo_set_mailbox_hidden` no longer reads back. After a successful `Set-Mailbox` it returns `requested_hidden`, `write_accepted: true`, `verified: false` and a `note` telling the caller to re-check with `exo_get_mailbox` after about 5 minutes. `_read_mailbox_until_hidden_matches` and its constants are gone. The response no longer contains `hidden_from_address_lists_enabled`, so a caller cannot mistake a same-call echo for the replicated state.
- Polling inside the tool was rejected: a same-call read proves nothing, and polling for minutes would hold the MCP call past gateway/agent timeouts. Verification belongs to a later step in the SOP.
- Tests: `test_set_mailbox_hidden_reports_pending_not_verified`, `test_set_mailbox_hidden_unhide_is_also_unverified`, `test_set_mailbox_hidden_reports_not_found`. `_FlipAfterNReads` was removed together with the retry tests.

## PRD-20394 · 2026-10-13

- Added `exo_get_auto_reply`/`exo_set_auto_reply` (`src/exo_mcp/tools/mailbox.py:391-486` @ `c0d53ea`, work branch `dev01.mbagent/PRD-20394`, not yet merged to `main` at the time of writing — this repo has no `int` branch, so there is no intermediate ref to cite; re-check this path:line once merged). Read/update a mailbox's automatic-reply configuration; a set call only touches fields it was given (relies on `invoke()`'s existing None-drop semantics, `api_client.py:239-241`) and performs exactly one post-write read-back.
- **`exo_set_auto_reply` does not do a precondition read before writing**, unlike `exo_set_mailbox_forwarding` (`:216-309` above). This is deliberate: the ticket's AC required exactly one `Get-MailboxAutoReplyConfiguration` call per successful `exo_set_auto_reply`, and a precondition read would make that two. Not-found for this mailbox is instead surfaced through the `Set-MailboxAutoReplyConfiguration` call's own error wording, classified by `_classify()` (`api_client.py:99-106`) the same way `exo_set_mailbox_hidden` already relies on it. Anyone adding a fourth mailbox-write tool here should decide this precondition-read-or-not question explicitly rather than copying whichever neighbor they saw last — the two existing tools disagree on purpose, not by accident.
- **The DateTime wire format is an unconfirmed assumption, not a verified fact**: `_parse_offset_datetime`/`_datetime_to_z` (`:69-121`) send `StartTime`/`EndTime` to `Set-MailboxAutoReplyConfiguration` as ISO-8601 UTC with a trailing `Z`, and `_normalize_upstream_time` (`:74-93`) assumes `Get-MailboxAutoReplyConfiguration` returns UTC-storable values in the same shape. Neither has been checked against a real tenant (see `docs/tickets/PRD-20394.md` § Tech design, Risks #1). If a real-tenant test later finds this wrong (the way `PRD-20321 follow-up` above found the hidden-mailbox readback assumption wrong), update this entry the same way that one was updated — supersede, don't silently edit.
- `external_audience`'s valid values are the literal strings `None`/`Known`/`All` (the real Exchange enum) — distinct from the Python `None` default meaning "field not supplied". A caller must pass the string `"None"` to explicitly request that audience value.
- Tests: `tests/test_mailbox_auto_reply.py`, one per AC (TC-EXO-007 through TC-EXO-016, TC-EXO-015 covering not-found for both tools).

## PRD-20480 · 2026-10-14

- New tool `exo_add_email_alias` (`src/exo_mcp/tools/mailbox.py` @ `3ec7afb`), placed right after `exo_set_mailbox_forwarding`. Additive `Set-Mailbox -EmailAddresses @{Add=[...]}` — existing primary/alias addresses are untouched; plain addresses get an `smtp:` prefix added, anything already containing a `:` is sent as-is (lets a caller set a new primary with an explicit `SMTP:` prefix). Rejects an empty `aliases` list locally before any Exchange round-trip, no cmdlet call for an obviously-bad request. Same `verified: false` + replication-delay note pattern as `exo_set_mailbox_hidden`/`exo_set_mailbox_forwarding` above — this module's third tool now carrying that caveat.
- The `{"Add": [...]}` wire shape is the first use in this file of a multi-valued Add/Remove cmdlet parameter — every prior `Set-Mailbox` tool here sets a scalar property. Not yet exercised against the real EXO REST endpoint (flagged in the design doc's own Option analysis, tracked as TC-EXO-004); if it is ever rejected, the documented fallback is read-merge-write via `exo_get_mailbox` + full-list `Set-Mailbox`, not implemented here since the additive form has no confirmed failure yet.
- Test coverage: `tests/test_tool_calls.py::test_add_email_alias_adds_multiple_without_disturbing_existing`, `::test_add_email_alias_rejects_address_in_use_elsewhere`, `::test_add_email_alias_rejects_empty_list_without_calling_exchange`, `::test_add_email_alias_not_found` (all added in this ticket, all passing at `3ec7afb`).
- Not covered by automated tests (needs a real tenant — see `docs/tickets/PRD-20480.md` § Self-test, TC-EXO-004): whether the real EXO REST endpoint actually accepts the `{"Add": [...]}` wire shape as-is, or needs the read-merge-write fallback.

## PRD-20480-r2 · 2026-10-19 (supersedes the PRD-20480 entry above)

- Real-tenant INT testing (comment `90170264109063`, Minnie Zhou, 2026-10-19) answered the open question the entry above flagged: the `{"Add": [...]}` wire shape **is rejected** by the real EXO REST endpoint with `invalid_argument "Invalid Operation"`. `exo_add_email_alias` (`src/exo_mcp/tools/mailbox.py` @ `a43db49`) now uses the documented fallback: `Get-Mailbox` reads the current `EmailAddresses`, each candidate address is checked with a precondition `Get-Recipient` (not found → available; resolves to this same mailbox → `already_present`; resolves elsewhere → `in_use_by_other`), only new addresses are merged into the full list and written with one `Set-Mailbox`, then a follow-up `Get-Mailbox` sets `verified`.
- The old "anything containing `:` is sent as-is" prefix handling is gone — it was the literal bug the real tenant exposed: an `"SMTP:"`-prefixed address silently changed the mailbox's primary. Only a bare address or an explicit lowercase `"smtp:"` prefix is now accepted; any other prefix is rejected per-address as `invalid`, not forwarded to Exchange (see `_invalid_alias_prefix`, new in `mailbox.py`).
- The response shape changed from a single `accepted`/`verified` boolean pair to a per-address `results: [{"address", "result": "added"|"already_present"|"in_use_by_other"|"invalid", "message"?}]` array — this is what AC5's "partial success" wording always required, but the pre-fix implementation could only ever fully succeed or fully fail on one Exchange error.
- `exo_get_mailbox`'s `_MAILBOX_FIELDS` now also projects `EmailAddresses`→`email_addresses` and `GrantSendOnBehalfTo`→`grant_send_on_behalf_to` — before this, "confirm with exo_get_mailbox" (the note both write tools return) had nothing to confirm with.
- New shared helper `contains_case_insensitive` (`src/exo_mcp/tools/_common.py`) does the case-insensitive membership check both this tool and `exo_add_sendonbehalf_permission` (`permissions.py`) need for their merge/dedup logic.
- Test coverage: `tests/test_tool_calls.py::test_add_email_alias_adds_multiple_without_disturbing_existing` and `::test_add_email_alias_rejects_address_in_use_elsewhere` were rewritten for the new call sequence (same judgement, different mocked cmdlets); new: `::test_add_email_alias_already_present_is_a_no_op`, `::test_add_email_alias_rejects_uppercase_smtp_prefix`, `::test_add_email_alias_rejects_other_prefixes`, `::test_add_email_alias_partial_success_writes_only_valid_addresses`, `::test_get_mailbox_reports_email_addresses_and_sendonbehalf`.
- Still not covered by automated tests (needs a real tenant — see `docs/tickets/PRD-20480-r2.md` § Self-test, TC-EXO-013): whether the new read-merge-write fallback itself round-trips correctly on a live tenant. This has not been fabricated as passing.
