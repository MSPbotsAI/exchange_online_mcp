### 方案选型

| 条目 | 方案 | 结论 |
|---|---|---|
| D1 wire 格式 | 保留 `{"Add": [...]}`，对 "Invalid Operation" 做重试/退避 | 否决——这个错误是确定性的（形状不对），不是瞬时的；重试只会每次都以同样方式失败。 |
| D1 wire 格式 | 读取-合并-写回完整列表（原技术设计已写明的兜底方案） | 采纳——正是文档里写的那条兜底；原「方案选型」里标注过的"对并发调用方不安全"风险照旧接受（同一身份、低流量对象，和 `exo_set_mailbox_forwarding` 自己那条先读后写同类风险）。 |
| D2 校验 | 靠 Exchange 自己写入时的拒绝来区分错误类型 | 否决——修复前的代码就是这么做的，Minnie 的 comment 恰好指出这是坏的："一个不存在的 delegate、一个被别人占用的 alias、一个被拒绝的格式，返回的都是同一个'Invalid Operation'"。 |
| D2 校验 | 写入前对每个候选值做一次 `Get-Recipient` 前置读取 | 采纳——把一个不透明的写入时 400 变成具体、可归因的结果（`invalid` / `in_use_by_other`），用的是 Exchange 自己返回的数据；而且 alias 循环能跳过一个坏地址继续处理其它的，不用整个调用中止。 |
| D4 前缀处理 | 继续接受任何带 `":"` 的前缀、原样发送（修复前行为） | 否决——这正是 Minnie comment 描述的那个 bug 本身：带 `"SMTP:"` 前缀的地址会悄悄改掉主地址，和"现有主地址保持不变"相矛盾。 |
| D4 前缀处理 | 只接受纯地址或显式小写 `"smtp:"` 前缀；其它一律按地址逐条拒绝 | 采纳——和 AC4 的原文（"现有主地址……保持不变"）完全对应，也契合 D2 已有的部分成功模型（一个坏地址不挡住其它地址）。 |
| D5 UPN 处理 | 文档里写明 `graph_add_group_owner` 需要 object id，工具本身不改 | 否决——本单范围内其它所有 Graph 工具都默默接受 UPN；只改文档会做出一个不一致、让人意外的 API。 |
| D5 UPN 处理 | 调用前先 `GET /users/{user_id}?$select=id` 解析，照搬 `graph_list_owned_groups` | 采纳——复用同一文件里已有、已测试过的写法，不另造一套。 |

### 数据与接口契约

- `exo_add_sendonbehalf_permission(identity, delegate) -> str`：成功时 `{"identity", "delegate", "result": "added"|"already_present", "granted": true, "verified"?, "note"?}`；`delegate` 经 `Get-Recipient` 解析不到时 `{"error": {"code": "invalid_argument", ...}}`；`identity` 解析不到时 `{"error": {"code": "not_found", ...}}`。调用顺序：`Get-Mailbox` → `Get-Recipient` → `Set-Mailbox -GrantSendOnBehalfTo <完整列表>` → `Get-Mailbox`（回读）。
- `exo_add_email_alias(identity, aliases) -> str`：`{"identity", "results": [{"address", "result": "added"|"already_present"|"in_use_by_other"|"invalid", "message"?}], "accepted": bool, "verified"?, "note"?}`。调用顺序：`Get-Mailbox` → 对每个候选地址 `Get-Recipient` → `Set-Mailbox -EmailAddresses <完整列表>`（仅当至少有一个地址是新的）→ `Get-Mailbox`（回读）。
- `exo_get_mailbox(identity, include_statistics) -> str`：`mailbox` 对象新增 `email_addresses: list[str]` 与 `grant_send_on_behalf_to: list[str]`（D3）。
- `graph_add_group_owner(group_id, user_id) -> str`：成功/已是所有者的返回形状不变（`{"group_id", "user_id", "status"}`）；`user_id` 现在接受 UPN 或 object id；返回的 `user_id` 始终是**解析后**的 object id，而不是调用方传入的原值，以跟 Graph 自己持有的数据保持一致；失败走标准信封。

### 关键流程时序

```
Agent -> exo-mcp: exo_add_email_alias(identity="shared@contoso.com", aliases=["old@contoso.com", "taken@contoso.com"])
exo-mcp -> Exchange: Get-Mailbox {Identity: "shared@contoso.com"}              -- 当前 EmailAddresses
exo-mcp -> Exchange: Get-Recipient {Identity: "old@contoso.com"}                -- 未找到 -> 可用
exo-mcp -> Exchange: Get-Recipient {Identity: "taken@contoso.com"}              -- 解析到另一个邮箱 -> in_use_by_other
exo-mcp -> Exchange: Set-Mailbox {Identity: "...", EmailAddresses: [<当前> + "smtp:old@contoso.com"]}
exo-mcp -> Exchange: Get-Mailbox {Identity: "shared@contoso.com"}              -- 回读，用于确定 verified
exo-mcp -> Agent: {results: [{address:"old@contoso.com", result:"added"}, {address:"taken@contoso.com", result:"in_use_by_other", message:"..."}], accepted: true, verified: ...}
```

### 非功能

- 额外往返：每个写工具现在最多要打 1 次（`Get-Mailbox`）+ N 次（每个候选 `Get-Recipient`，仅 alias 工具）+ 1 次（`Set-Mailbox`，若没有新地址则跳过）+ 1 次（`Get-Mailbox` 回读），相比原来单次调用的设计多了几步。接受这个代价——正确性（能区分失败原因、不破坏已有列表）胜过多出来的延迟，毕竟这是有意为之、低频的管理操作，不是热路径。
- 并发：读取-合并-写回这段窗口对同一邮箱同一属性的并发写入者不安全——这在原技术设计的「方案选型」里就标注过是可接受的风险，本轮未变。
- 向后兼容：两个写工具的返回形状都变了（`exo_add_sendonbehalf_permission` 新增了 `result` 字段，不再只靠一个裸的 `granted`；`exo_add_email_alias` 用逐地址 `results` 数组取代了原来只有 `aliases_requested`/`accepted` 的形式）。这对按旧形状解析的调用方是破坏性改动——这里认为可接受，因为旧形状对一个在真实租户上实际失败的调用也会报成功（`"granted": true` / `"accepted": true`，即 D1），所以不可能有调用方是"正确地"依赖着旧形状的。
- 多租户隔离：未变——仍是同一套按请求的 `client_factory()`/`GraphClient` 接线；没有引入新的跨租户面。
