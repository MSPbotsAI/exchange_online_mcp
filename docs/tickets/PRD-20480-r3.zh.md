## 现状（每条陈述都带 path:line）

以本轮的基线（`exchange_online_mcp@main` @ `fc0021c`，即第二轮工作合入 `main` 的那个合并提交）为准：

- `exo_add_email_alias`（`src/exo_mcp/tools/mailbox.py:653-657` 修复前）在 `try`/`except ExoError` 里执行 `recipients = await client.invoke("Get-Recipient", {"Identity": local})`，**任何**异常都被记成 `{"result": "invalid", "message": exc.message}` 并 `continue`——没有一条分支专门处理"这次查询本身就是在说这个地址还不存在"。真实 Exchange 对未被占用的地址执行 `Get-Recipient -Identity <未占用地址>` 会返回一个 HTTP 400、正文包含 `"couldn't be found"`，`api_client.py:89-101` 的 `_classify` 早就把这类文本映射成 `code="not_found"`——但 `mailbox.py` 在判定地址无效之前从未读取过 `exc.code`。INT 看到的现象（"每一个新的（未占用）地址都被判为 'invalid'"）是这个代码结构的必然后果：没有任何路径能让一个全新地址走到 `results.append({"result": "added"})`。
- 第二轮的单元测试（`tests/test_tool_calls.py::test_add_email_alias_adds_multiple_without_disturbing_existing`、`::test_add_email_alias_partial_success_writes_only_valid_addresses`）用 `upstream.responses["Get-Recipient"] = []` 来模拟"空闲地址"——这是**200 OK 加一个空列表**，而 mock 端 `Upstream.handler`（`tests/conftest.py:61-82`）只有在该 cmdlet 没有设置 `cmdlet_errors` 时才会这样回应。真实 Exchange 对一个未使用的 identity 并不会这样回应（它是 400 错误，不是 200 空列表），所以这两条测试都从未真正跑进那个真正有 bug 的 `except ExoError` 分支。这正是 Minnie comment 里指出的"第一轮测试没能抓住这个 bug"的根因——`#AC4`/TC-EXO-002 的 mock 与真实行为不符。
- `exo_add_sendonbehalf_permission` 的 already_present 判断（`src/exo_mcp/tools/permissions.py:171-175` 修复前）会拿委托人字符串、`Get-Recipient` 的 `Identity`、以及它的 `PrimarySmtpAddress` 去跟邮箱当前的 `GrantSendOnBehalfTo` 列表比对，但从未比对过 `ExternalDirectoryObjectId`——而这恰恰是 `Set-Mailbox` 写入复制完成后，EXO 真正存进 `GrantSendOnBehalfTo` 里的字段（INT 已确认：`GrantSendOnBehalfTo` 里存的是类似 `c1dcd1cd-...` 的 GUID，不是邮箱地址）。复制窗口内的重复调用会绕过前面那些基于 UPN/SMTP 的快速匹配，落到这个缺了 object id 比对的分支，于是再次报告 `added`。
- `_invalid_alias_prefix`（`src/exo_mcp/tools/mailbox.py:198-209` 修复前）对所有被拒绝的前缀使用同一条消息，措辞围绕"会改变邮箱的主地址"——这只对 `"SMTP:"` 成立；Exchange 对 `"x500:"` 或其它前缀并不是这样处理的，所以这条消息对每一个非 `"SMTP:"` 的情形都描述错了实际后果。
- 两个写工具的描述都没有提到"重复调用可能落在尚未完成的复制窗口内"——这既是 N3 的根因，也是 N4 的诉求，一个专门针对 `exo_add_sendonbehalf_permission`（N3），一个泛指两个工具（N4）。

- `src/exo_mcp/tools/permissions.py` —— `exo_add_sendonbehalf_permission` 的 `already_present` 判断（N3）；工具 docstring（N3 提示 + N4）

### 方案分析

| 项目 | 方案 | 结论 |
|---|---|---|
| N1 | 把 `Get-Recipient` 的每个 `ExoError` 都当 `invalid`（修复前行为） | 否决——这就是字面意义上的 bug：一个空闲地址抛出的异常类型跟真正的失败一模一样，两者被同等处理。 |
| N1 | 判断 `exc.code == "not_found"`，等同于空的 `recipients` 列表（地址空闲）；其它错误码仍记 `invalid` | 采纳——用的是 `api_client.py` 已经分类好的信号，不引入新的错误码体系；真正的其它失败（比如格式错误的 identity、限流）仍然会正确地把该地址挡下为 `invalid`，而不是把未知失败也当"空闲"处理。 |
| N1 | 把 `Get-Recipient` 的任何错误都当"地址空闲"（一律写入） | 否决——会在前置检查本来就判断不了的情况下（比如上游临时故障）悄悄写入一个别名，比现在"过度保守地判 invalid"更糟。 |
| N2 | 所有被拒绝的前缀共用一条消息 | 否决——"会改变主地址"这个说法对非 `SMTP:` 前缀是错的，会误导看到这条错误文案的人。 |
| N2 | 两条消息：`"SMTP:"` 专门点名主地址后果，其它前缀用另一条 | 采纳——如实反映 Exchange 的实际行为；只改消息，不改行为。 |
| N3 | 维持 already_present 只比对 UPN/SMTP | 否决——INT 已确认复制窗口内的重复调用会报告两次 `added`，正是 comment 描述的现象。 |
| N3 | 额外把 `Get-Recipient` 的 `ExternalDirectoryObjectId` 拿去跟当前 `GrantSendOnBehalfTo` 列表比对 | 采纳——如实匹配 EXO 复制完成后真正存储的内容；comment 里标的是"可选"，但本轮仍然实现了，因为改动很小、范围局部、风险低，能真正堵上这个缺口而不只是写文档说明。 |
| N4 | 不改文档 | 否决——comment 明确要求在两个工具上都加这句话。 |
| N4 | 给两个写工具的描述各加一句复制窗口提示 | 采纳——直接对应诉求；措辞尽量精简，以满足本仓 `test_tools_list_snapshot` 的 500 字符描述上限（`tests/test_tools.py:69`）——两处改动后的 docstring 都需要重新裁剪以满足这条门禁。 |

### 数据与接口契约

响应结构无变化。`exo_add_email_alias` 的 `results[].result` 现在对一个全新地址确实能返回 `"added"`（此前因 N1 实际上不可达）；`invalid` 结果的 `message` 文案按前缀不同而不同（N2）。`exo_add_sendonbehalf_permission` 的 `already_present` 结果现在多了一种可达路径（仅 object-id 匹配，N3），没有新增字段。

### 关键流程/时序

```
Agent -> exo-mcp: exo_add_email_alias(identity="alice@contoso.com", aliases=["new@contoso.com"])
exo-mcp -> Exchange: Get-Mailbox {Identity: "alice@contoso.com"}            -- 当前 EmailAddresses
exo-mcp -> Exchange: Get-Recipient {Identity: "new@contoso.com"}            -- 400 "couldn't be found" -> ExoError(code=not_found)
exo-mcp（N1 修复）: code == "not_found" -> 等同 recipients=[] -> 地址空闲 -> 加入待写入列表 "smtp:new@contoso.com"
exo-mcp -> Exchange: Set-Mailbox {Identity: "...", EmailAddresses: [<当前地址> + "smtp:new@contoso.com"]}
exo-mcp -> Exchange: Get-Mailbox {Identity: "alice@contoso.com"}            -- 读回确认，设置 verified
exo-mcp -> Agent: {results: [{address:"new@contoso.com", result:"added"}], accepted: true, verified: ...}
```

- 风险（不变，沿用自第二轮）：两个写工具的读取-合并-写回窗口对同一邮箱同一属性的第二个并发调用者并不安全。N4 新增的文档提示正是把这条注意事项向调用方明说，并不改变底层风险本身。
