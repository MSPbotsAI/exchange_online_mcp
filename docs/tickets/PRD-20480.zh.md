## 需求理解

一句话：提单人要在两个现有 MCP —— Microsoft Graph（ms-graph）与 Exchange Online（exchange-online）—— 上各补几个缺失的工具/参数（共 5 项），使 M365 入职/离职以及邮箱/Teams 权限配置类工作流能端到端跑完，不需要人再手动去 M365/Exchange 管理后台补一步。

提单人原话列出的 5 项（工具名由提单人建议、用在哪一步、加到哪个 MCP、需要的参数）：
1. `graph_create_tap`（ms-graph）—— 给新员工生成一次性/限次使用的临时登录码（E6），只发给经理。
2. `exo_add_sendonbehalf_permission`（exchange-online）—— 给共享邮箱授予"代表发送"权限（E5）。
3. `exo_add_email_alias`（exchange-online）—— 给邮箱添加一个或多个别名/旧地址（E5，表单第 14 题）。
4. `graph_add_group_owner`（ms-graph）—— 设置群组/Teams 所有者，前提是审批已在别处完成（E5）。
5. `graph_create_user` / `graph_update_user` 新增 `preferred_language` 参数 —— 设置新员工界面语言，例如 `fr-CA` / `en-CA`（E2/E3）。

提单人已自行做过查重，对比 PRD-20422（"[Feature] Graph offboarding transfer and sync"）—— 已核对不是重复。提单人确认："Q1 A, A"。提单人：Felix.Zhou@mspbots.ai，提交于 2026-10-14（UTC+8），渠道 Teams。

## 产品设计

### 目标 / 非目标

目标：
- 按提单人列出的参数名，在指定的 2 个 MCP 里精确补齐这 5 个工具/参数。
- 每个新工具/参数一旦被该 agent 的 connector 授权（见"现状"），agent 就能用它完成对应的入职/离职步骤，不需要人再去 M365 管理中心或 Exchange 管理中心手动操作。

非目标（本单明确不做）：
- 不新建 MCP/connector。`ms-graph-mcp` 与 `exchange_online_mcp` 都已存在，且已在平台上连接。
- 这 3 个新写工具（`exo_add_sendonbehalf_permission`、`exo_add_email_alias`、`graph_add_group_owner`）都不做"移除"的对应工具 —— 工单只要求了"添加"方向，这与两个仓库现有"一个工具一个固定动词"的约定一致（例如 `exo_add_mailbox_permission` / `exo_remove_mailbox_permission` 是两个独立工具；未来若要补移除能力，应走同样的方式另立一单）。
- 不做群组/Teams 所有权的审批工作流 UI。工单原话"Teams 只有经过批准才设为所有者"描述的是发生在 agent 调用 `graph_add_group_owner` **之前**的人工/SOP 层审批步骤；本单只建"设置所有者"这个机械动作本身。
- 不改平台侧的 OAuth scope 授予或租户重新授权流程（那在另一个仓库 `MCP-Management-Service` 的 `auth/oauth/vendors/msgraph.py` 里 —— 不是本单 Code Project 的选项，也不在本单覆盖的两个仓库里）。5 项里有 2 项依赖它，原因见技术设计 §8。

### 验收标准 AC1..ACn

- AC1（TAP）：Given agent 已连接 `ms-graph-mcp` 且 `graph_create_tap` 已对其授权，When agent 对一个有效用户调用 `graph_create_tap` 且不传任何可选参数，Then 返回的临时登录码在其有效期内恰好可用一次（默认一次性，与工单 E6 场景"只发给经理"的描述一致）；When agent 传入 `is_usable_once=false` 与显式的 `lifetime_minutes`，Then 返回的登录码遵循这些设置。
- AC2（TAP，异常路径）：Given 一个无效或不存在的 `user_id`，When 调用 `graph_create_tap`，Then 工具返回结构化错误（标明用户未找到），而不是抛出原始异常。
- AC3（SendOnBehalf）：Given 一个共享邮箱与一个尚无 SendOnBehalf 权限的被授权人，When agent 调用 `exo_add_sendonbehalf_permission(mailbox, delegate)`，Then 该被授权人获得该邮箱的 SendOnBehalf 权限（待 EXO 复制完成后可用 `exo_get_mailbox` 核实）。
- AC4（别名）：Given 一个邮箱与一个或多个租户内尚未被占用的别名地址，When agent 在一次调用里对 `exo_add_email_alias(mailbox, aliases=[...])` 传入一个或多个地址，Then 每个有效地址都被加入该邮箱的地址列表，且邮箱原有的主地址与其它别名保持不变。
- AC5（别名，异常路径）：Given 一个已被租户内其它收件人占用的别名地址，When 用它调用 `exo_add_email_alias`，Then 工具如实暴露 Exchange 对该地址的拒绝，而不是静默丢弃；同一次调用里的其它有效地址仍然各自被处理，整体结果能清楚看出哪些成功、哪些没有。
- AC6（群组所有者）：Given 一个群组/Team id 与一个当前不是所有者的用户 id，When agent 调用 `graph_add_group_owner(group_id, user_id)`，Then 该用户成为该群组/Team 的所有者；When 对一个已经是所有者的用户重复同样的调用，Then 工具报告"已满足"而不是失败（与 `graph_assign_groups` 对群组成员已有的幂等行为一致）。
- AC7（preferred_language）：Given 一个合法的 BCP-47 语言标签（如 `fr-CA`、`en-CA`），When 在创建时传给 `graph_create_user`、或对已有用户传给 `graph_update_user`，Then 该用户的 `preferredLanguage` 属性被设置为该值，后续 `graph_get_user` 读取可见。
- AC8（权限与多租户，质量线强制要求）：Given 调用方的 token/凭据被限定在租户 A（即两个仓库现有的、每个工具都在用的按请求 `client_factory()` / 按租户 app 注册这套机制），When 调用这 5 个新工具/参数中的任意一个，Then 不存在任何代码路径或参数能让调用方指向另一个租户的目录/邮箱 —— 租户隔离完全继承自现有的按请求凭据机制，本单新增的逻辑不引入任何新的跨租户面。

本单横跨两个独立仓库。下面两个子节是两份互相独立的实现方案，谁都不阻塞谁，可以拆成两个 PR 并行推进。

### A. ms-graph-mcp —— `graph_create_tap`、`graph_add_group_owner`、`preferred_language`

#### 结论

三处小的、增量式改动，分别加到两个现有工具模块里，都照着本仓库已有的形状写：(1) 在 `users.py` 里紧挨着现有 `/authentication/*` 工具新增一个工具，调用 Graph 的 TAP 创建端点；(2) 在 `groups.py` 里紧挨着现有成员管理工具新增一个工具，复用已经定义好的 `_DIRECTORY_OBJECT_URL` 辅助量；(3) 给两个现有的用户写工具各加一个可选参数。不需要给 `GraphClient` 加任何新方法（`post` 已经有了）。唯一真实的成本是两个新 Graph 权限范围，需要另一个仓库/团队去授予（见 §8）。

#### 数据与接口契约

- `graph_create_tap(user_id: str, start_date_time: str | None, lifetime_minutes: int | None, is_usable_once: bool = True) -> str`（JSON）：
  - 请求：`POST /users/{user_id}/authentication/temporaryAccessPassMethods`，body `{"startDateTime": <iso8601>?, "lifetimeInMinutes": <int 10..43200>?, "isUsableOnce": <bool>?}`。
  - 响应（成功，201）：回显 `{"user_id", "temporary_access_pass", "lifetime_minutes", "is_usable_once", "is_usable", "method_usability_reason"}` —— 字段名直接取自 Graph 的 `temporaryAccessPassAuthenticationMethod` 响应。
  - 错误：`GraphError` 原样透传 —— scope 缺失或租户未重新授权时 403（见 §8）、`user_id` 解析不到时 404。
  - 安全提示：`temporary_access_pass` 是一次性登录密钥。Graph 的 API 契约要求必须返回它（之后无法再取回），所以 MCP 别无选择只能把它放进工具响应 —— 和其它任何 MCP 工具返回值的暴露面是同一类，本单不新增任何日志落点，也不新增任何持久化它的代码路径。
- `graph_add_group_owner(group_id: str, user_id: str) -> str`（JSON）：`{"group_id", "user_id", "status": "added" | "already_owner" | "error", "detail"?}`。请求：`POST /groups/{group_id}/owners/$ref`，body `{"@odata.id": "https://graph.microsoft.com/v1.0/directoryObjects/{user_id}"}`。Graph 成功时返回 `204 No Content`（无 body），处理风格与现有 members/$ref 调用一致。
- `preferred_language` —— 不新增端点；作为 `"preferredLanguage": "<BCP-47 标签>"` 追加进现有的 `graph_create_user`/`graph_update_user` 请求体。

#### 关键流程时序

```
Agent -> graph-mcp: graph_create_tap(user_id="...", is_usable_once=true)
graph-mcp -> Graph API: POST /users/{id}/authentication/temporaryAccessPassMethods
Graph API -> graph-mcp: 201 { temporaryAccessPass: "...", isUsable: false, methodUsabilityReason: "NotYetValid"（若 startDateTime 在未来）}
graph-mcp -> Agent: { temporary_access_pass: "...", ... }
Agent -> （SOP 层面）只把这个 pass 交给该用户的经理
```

#### 非功能

- 幂等与并发：`graph_add_group_owner` 按设计是幂等的（已是所有者 → `already_owner`，不是错误），与 `graph_assign_groups` 一致。`graph_create_tap` 明确**不**幂等 —— Graph 第二次调用会替换掉已有的 TAP —— 所以标注 `idempotentHint=False`，docstring 也要写清楚，与本文件里 `graph_create_user` 对密码一次性语义的既有提示风格一致。
- 性能：两者都是单次同步 Graph 调用，无分页，不新增性能面。

#### 方案选型

| 项 | 方案 | 结论 |
|---|---|---|
| SendOnBehalf | `Set-Mailbox -GrantSendOnBehalfTo @{Add=<delegate>}`（增量式） | 首选 —— 符合工单"单个被授权人、添加"的语义，也符合本仓库"一个工具一个固定动词"的既有约定。**若 Add 哈希表线上格式被拒绝的兜底方案**：先用 `exo_get_mailbox` 读出邮箱当前的 `GrantSendOnBehalfTo` 列表，追加该被授权人，再 `Set-Mailbox -GrantSendOnBehalfTo <完整列表>` —— 功能等价，但对并发调用不是竞态安全的；只有增量式格式不工作时才用这个。 |
| SendOnBehalf | `Add-RecipientPermission`（授予的是 SendAs，不是 SendOnBehalf） | 拒绝 —— 权限语义不对；这是（尚未建的）SendAs 对应工具该用的 cmdlet，不是本单要的。 |
| 别名 | `Set-Mailbox -EmailAddresses @{Add="smtp:<地址>"}`（增量式，一次调用可传多个地址） | 首选 —— 符合工单明确要求的"保留多个旧地址/别名"。若线上格式被拒绝，兜底方案与 SendOnBehalf 同理。 |
| 别名 | `Set-Mailbox -Alias <name>` | 拒绝 —— 这是 Exchange 老式的单个 `mailNickname` 风格别名，不是工单要的那种可多个并存的 proxy address 列表（工单原话明确是"别名或旧地址保留"，明确支持多个）。 |

#### 数据与接口契约

- `exo_add_sendonbehalf_permission(identity: str, delegate: str) -> str`（JSON）：`{"identity", "delegate", "granted": true, "verified": false, "note": "<复制延迟说明，照抄 mailbox.py 现有措辞>"}`。Cmdlet：`Set-Mailbox -Identity <identity> -GrantSendOnBehalfTo @{Add=<delegate>}`。错误：`ExoError` 原样透传 —— 邮箱或被授权人找不到；"被授权人已被授予过"的具体行为是唯一的待核实用例（见上）。

#### 关键流程时序

```
Agent -> exo-mcp: exo_add_email_alias(identity="shared@contoso.com", aliases=["old-name@contoso.com"])
exo-mcp -> Exchange（REST PowerShell）: CmdletInput { CmdletName: "Set-Mailbox", Parameters: { Identity: "...", EmailAddresses: { Add: ["smtp:old-name@contoso.com"] } } }

exo-mcp -> Agent: { identity, aliases_requested, accepted: true, verified: false, note: "几分钟内完成复制；用 exo_get_mailbox 核实" }
```

- 多租户隔离：不变 —— 与现有每个工具一样的按租户 app 注册 + `Recipient Management` 角色边界（对应 AC8）。
