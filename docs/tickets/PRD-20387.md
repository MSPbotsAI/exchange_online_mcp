## Requirement understanding

One line: Add 6 Exchange Online connector tools so MSPbots can manage mailbox FullAccess and SendAs permissions for the migrated Ginko Rewst flow instead of requiring manual technician execution.

The reporter (Felix.Zhou@mspbots.ai) is migrating a Rewst automation (`[Ginko] EXO: Manage Mailbox Permissions`) onto the MSPbots platform. That Rewst flow calls 6 Exchange Online cmdlets directly to grant/revoke/view mailbox FullAccess and SendAs permissions. The reporter already checked both the platform's existing Exchange Online connector and its Microsoft Graph connectors (delegated and app-only) and confirmed neither exposes an equivalent capability — Graph has no mailbox-permission object (see Current state). Success is exact functional parity: the 6 cmdlets below, reachable as MCP tools with the stated fixed access rights, so the migrated flow no longer needs a technician to run them by hand.

## Product design

### Goals / Non-goals

- Goal: add exactly the 6 tools the ticket lists, each wrapping its named cmdlet 1:1, with the access right fixed as specified (not caller-settable).
- Goal: match the existing 7 tools' error shape, field-projection style and credential handling so the connector stays one coherent surface.
- Non-goal: any tool that accepts an arbitrary `AccessRights` value. The ticket is explicit that `FullAccess` / `SendAs` are fixed, not parameters — generalizing this would be solving a problem nobody asked for (the connector already shows this restraint: `exo_remove_distribution_group_member` doesn't take an "access right" either).
- Non-goal: bulk operations (e.g. apply to N mailboxes in one call). The ticket's Minimal Viable Slice is explicit: "Exactly these 6 tools with the specified parameters and fixed access rights."
- Non-goal: any platform/UI-side change. Per Current state, the connector's tool list is auto-discovered; there is nothing to build outside this repo.
- Non-goal: changing `_NOT_FOUND_MARKERS` or any other shared error-classification code — the existing not-found detection already covers "mailbox/recipient does not exist" for any cmdlet, including the 6 new ones.

### Acceptance criteria AC1..ACn

- AC1: Given a valid mailbox identity and trustee, when `exo_add_mailbox_permission(identity, user)` is called, then the trustee is granted FullAccess on that mailbox and the tool returns a success result naming the mailbox, the trustee and `FullAccess`.
- AC2: Given `exo_add_mailbox_permission` is called with `auto_mapping=False`, when the grant succeeds, then the trustee's Outlook profile does not auto-add the mailbox (the call must pass `AutoMapping=false` to Exchange, not just omit it).
- AC3: Given a mailbox identity and a trustee that currently has FullAccess, when `exo_remove_mailbox_permission(identity, user)` is called, then the trustee's FullAccess is revoked and the tool returns a success result naming the mailbox and the trustee.
- AC4: Given a valid mailbox identity and trustee, when `exo_add_recipient_permission(identity, trustee)` is called, then the trustee is granted SendAs on that mailbox and the tool returns a success result naming the mailbox, the trustee and `SendAs`.
- AC5: Given a mailbox identity and a trustee that currently has SendAs, when `exo_remove_recipient_permission(identity, trustee)` is called, then the trustee's SendAs is revoked and the tool returns a success result naming the mailbox and the trustee.
- AC6: Given a mailbox that has one or more trustees with FullAccess, when `exo_get_mailbox_permission(identity)` is called without `user`, then the tool returns every such trustee (not the mailbox owner's own default self-grant) with the access right(s) each holds.
- AC7: Given a mailbox and a specific trustee, when `exo_get_mailbox_permission(identity, user=<trustee>)` is called, then the result is narrowed to that trustee only (empty list if that trustee has no FullAccess grant, not an error).
- AC8: Given a mailbox that has one or more trustees with SendAs, when `exo_get_recipient_permission(identity)` is called without `trustee`, then the tool returns every such trustee.
- AC9: Given a mailbox and a specific trustee, when `exo_get_recipient_permission(identity, trustee=<trustee>)` is called, then the result is narrowed to that trustee only (empty list if none, not an error).
- AC10: Given an `identity` (and, for add/remove, a `user`/`trustee`) that does not resolve to a real mailbox/recipient, when any of the 6 tools is called, then the tool returns the standard `{"error": {"code": "not_found", ...}}` envelope, not a raised exception and not a generic 400.
- AC11: Given no Exchange Online credentials are present on the request (no certificate/secret headers reached the connector), when any of the 6 tools is called, then the tool returns the existing `NO_CREDENTIALS` envelope, matching the behaviour of all 7 existing tools.
- AC12: Given two different tenants' credentials arrive on two concurrent requests, when any of the 6 tools runs for each, then each sees only its own tenant's data — no new module-level or cross-request state is introduced by this change (reuses the existing per-request `ExoClient`/contextvar isolation).
- AC13: Given the connector is already connected on the platform, when the 6 new tools are deployed and an operator presses "Refresh Tools" on the connector detail page, then all 6 appear in the per-connector tool list with name and one-line description, with no other platform-side change required (wiki: `ProductDocs/15-Capabilities.md § Connector detail view`, `_verified_ 2026-08-28`).

### Open questions

- [已假设] The ticket does not say whether `exo_get_mailbox_permission` / `exo_get_recipient_permission` should include the mailbox owner's own implicit self-grant (`NT AUTHORITY\SELF`, present on effectively every mailbox) in the result. This design assumes **no** — it is never an actionable trustee for the stated purpose ("view and delete confirmation"), and every other list-style tool in this connector (e.g. `exo_list_mobile_devices`) already returns only agent-actionable records, not platform noise. If this assumption is wrong, AC6/AC8 need a parameter or a documented flag to restore it; §4 "Change list" below isolates the filter in one place so that is a small change.
- [不阻塞] `auto_mapping` has no stated default in the ticket. This design defaults it to `True`, matching Exchange's own `Add-MailboxPermission -AutoMapping` default, so a caller who omits the parameter gets the same behaviour as calling the cmdlet directly. Can be changed to default `False` later without breaking the contract (the parameter already exists).
- [不阻塞] The exact property names Exchange returns from `Get-MailboxPermission` / `Get-RecipientPermission` (used for field projection) are taken from Microsoft's published cmdlet reference, not from a live call against this tenant (no EXO tenant is reachable from the design flow). The dev leg's existing test pattern — unit tests against a mocked upstream (`tests/conftest.py`), plus the no-tenant e2e harness (`tests/mock_e2e/`) — already catches a wrong field name before anything ships; this is flagged as a verify-during-implementation item, not a blocker.

## Tech design

### Conclusion

Add one new tool module, `src/exo_mcp/tools/permissions.py`, following the exact shape `groups.py` already established (one `register(mcp, client_factory)` function, one `@mcp.tool` per cmdlet, `client.invoke(cmdlet, params)`, `ExoError` → `exc.to_envelope()`). No change to `api_client.py`'s classification logic, no new credential plumbing, no new dependency. This is the cheapest correct option because the connector already has every piece this feature needs (REST cmdlet client, error envelope, field projection, per-tenant isolation) — the only new code is 6 thin tool functions plus their tests and README rows.

### Where the current implementation lives

- `src/exo_mcp/tools/mailbox.py:91-301` — the module to copy the shape from most closely (projection, verify-after-write pattern for `Set-*` tools).
- `src/exo_mcp/tools/groups.py:1-67` — the closer precedent specifically for an Add-/Remove-style (non-`Set-`) cmdlet pair acting on a relationship rather than a scalar property; `exo_remove_distribution_group_member` (`groups.py:16`) is structurally the nearest existing tool to the 4 new write tools.
- `src/exo_mcp/tools/_common.py:13-28` — `NO_CREDENTIALS` sentinel and `project()` helper, reused as-is.
- `src/exo_mcp/api_client.py:77-103` — status/error classification; `_NOT_FOUND_MARKERS` already generic across cmdlets, reused as-is.
- `src/exo_mcp/server.py:108-148` — `create_mcp_server`: where new modules get imported and registered, and where the agent-facing `instructions` string documents typical tool sequences.
- `README.md:29-39` — the Tools table, the connector's published contract.
- `tests/test_tools.py:17-41` — the tool-set snapshot that must be extended or it fails closed (by design — it is the outward contract).
- `tests/test_tool_calls.py:1-45` — the call-level test pattern (mock upstream, assert projected fields and exact cmdlet parameters sent).
- `tests/mock_e2e/mock_upstream.py:17-...` — cmdlet → fixture map for the real-container e2e harness.

### Option analysis

No real alternative design exists at the "where does this code go" level — the ticket asks for 6 cmdlet wrappers on a connector that already wraps 7 cmdlets from the same cmdlet family (Exchange admin `InvokeCommand`), with an established, tested pattern for exactly this shape of tool. The only decision with more than one reasonable answer is **one module vs. extending `mailbox.py`**:

| Option | Approach | Pros | Cost | Verdict |
|---|---|---|---|---|
| A | New `permissions.py` module | Matches the existing one-module-per-area layout (`mailbox` / `groups` / `devices`); permissions are a distinct concern from mailbox property reads/writes; keeps `mailbox.py` (already 301 lines) from growing further | One more `import` + one more `register()` call in `server.py` | **Chosen** |
| B | Add the 6 tools into `mailbox.py` | Slightly less boilerplate (no new file) | Breaks the area-per-module convention (permissions are not a mailbox property); makes the already-largest file larger for no benefit | Rejected |

### Data & API contract

This connector has no database and no outbound events — every tool is a direct pass-through to the Exchange admin REST endpoint. Contract is therefore: MCP tool signature in, Exchange `InvokeCommand` call out, projected JSON back.

- `exo_add_mailbox_permission`
  - Request (MCP tool args): `{"identity": "alice@contoso.com", "user": "bob@contoso.com", "auto_mapping": true}`
  - Upstream call: `POST {base}/adminapi/beta/{tenant}/InvokeCommand` with `CmdletName: "Add-MailboxPermission"`, `Parameters: {"Identity": "alice@contoso.com", "User": "bob@contoso.com", "AccessRights": ["FullAccess"], "AutoMapping": true}`
  - Success response: `{"identity":"alice@contoso.com","user":"bob@contoso.com","access_rights":["FullAccess"],"granted":true}`
  - Error response (unresolved mailbox/user): `{"error":{"code":"not_found","message":"...","retryable":false}}`
- `exo_remove_mailbox_permission` — same shape, `{"identity":...,"user":...,"access_rights":["FullAccess"],"removed":true}` on success.
- `exo_add_recipient_permission` / `exo_remove_recipient_permission` — same shape with `trustee` instead of `user`, `AccessRights: ["SendAs"]`, result key `granted`/`removed`.
- `exo_get_mailbox_permission`
  - Request: `{"identity": "alice@contoso.com"}` or `{"identity": "alice@contoso.com", "user": "bob@contoso.com"}`
  - Success response: `{"identity":"alice@contoso.com","trustees":[{"user":"bob@contoso.com","access_rights":["FullAccess"],"deny":false,"is_inherited":false}]}` (empty `trustees` list, not an error, when none match)
- `exo_get_recipient_permission` — same shape, key `trustees`, each entry `{"trustee":...,"access_rights":["SendAs"],"access_control_type":"Allow","is_inherited":false}`.
- No DB changes, no migration, no backfill — this connector is stateless per request (confirmed: `src/exo_mcp/api_client.py` holds no persistent store, `server.py` contextvar is reset after every request).
- Backward compatibility: purely additive. No existing tool's name, parameters or response shape changes; `tests/test_tools.py:40` (`assert names == set(EXPECTED_TOOLS)`) is itself the regression guard for "did an existing tool get renamed/removed by accident."

### Key flow / sequence

Typical caller flow (new section of the `instructions` string, §4 Change list):

```
1. exo_get_mailbox_permission(identity) / exo_get_recipient_permission(identity)
   -> agent sees current trustees before acting
2. exo_add_mailbox_permission(identity, user) or exo_add_recipient_permission(identity, trustee)
   -> Exchange grants the fixed right
3. (later) exo_remove_mailbox_permission / exo_remove_recipient_permission
   -> Exchange revokes it
```

Per-call sequence (identical for all 6, matches the existing tools):

```
MCP client -> FastMCP tool function
  -> client_factory() reads ExoCredentials from the request-scoped contextvar
  -> ExoClient.invoke(cmdlet, params)
       -> _access_token() mints/reuses a per-request token (fetch_access_token, auth.py)
       -> POST {base}/adminapi/beta/{tenant}/InvokeCommand
       -> Exchange runs the cmdlet, returns records or an error body
  -> project()/filter the result, or ExoError.to_envelope() on failure
  -> JSON string returned to the MCP client
```

### Non-functional

- **Idempotency & concurrency**: the 4 write tools are **not** naturally idempotent — `Add-MailboxPermission` errors if the exact grant already exists, `Remove-MailboxPermission` errors if it doesn't. This design does **not** swallow those errors into a synthetic success (unlike the `Set-*` tools in `mailbox.py`, which are naturally idempotent because `Set-` cmdlets are). Instead it follows the one existing precedent for this exact shape — `exo_remove_distribution_group_member` (`groups.py:16`, `idempotentHint=False`) — and reports the real cmdlet failure through the standard envelope. Marking these 4 tools `idempotentHint=False` (matching that precedent) is honest about the risk rather than hiding it, and AC6–AC9's read tools exist precisely so a caller can check state before mutating it. Concurrency: each request gets its own `ExoClient` instance (`server.py:39-43`), so two concurrent grants on different mailboxes never interfere; two concurrent grants on the *same* mailbox+trustee race at the Exchange API level exactly as two concurrent `Add-MailboxPermission` PowerShell calls would — not a regression introduced by this change.
- **Performance**: single upstream call per tool (the 2 read tools do not do a verify-after-write read-back the way `mailbox.py`'s `Set-*` tools do, because there is nothing to re-verify beyond what `Get-*Permission` itself returns). Same timeout/retry budget as every other tool (`api_client.py:49-55`, 2 retries, 30s read timeout) — no new timeout tuning needed.
- **Security**: no new credential surface — reuses the existing per-request, header-only credential contextvar (`server.py:32-105`); no credential or permission data is logged (this connector logs nothing by design — confirmed no `logging`/`print` calls exist in `src/exo_mcp/`). Authorization is enforced entirely by Exchange's own RBAC (the app's `Recipient Management` role assignment) — this connector does not and should not re-implement an authorization check; a 403 from Exchange surfaces as `unauthorized` via the existing `_STATUS_HINTS` message (`api_client.py:171-180`), unchanged by this ticket.
- **Multi-tenant isolation**: unchanged mechanism — one tenant's credentials per request via `X-Exo-Tenant-Id` + cert/secret headers, isolated by `contextvars` so concurrent requests from different tenants never share state (`server.py:32-45`). The 6 new tools introduce no module-level or shared state, so they inherit this guarantee without new code to audit.
- **Observability**: unchanged — this connector has no logging today (errors are returned to the caller, not logged server-side); this is consistent with the rest of the connector and out of scope to change here. If this needs to change, it's a connector-wide decision, not specific to this ticket.

### Rollout & rollback

- No feature flag — this repo has none (`grep` for `flag`/`toggle` in `src/` is empty) and the 6 tools are purely additive, so there is no user-visible transition to gate.
- Rollout: merge → container rebuild/redeploy (per `Dockerfile`/`docker-compose.yml`) → the already-connected Exchange Online connector instance picks up the new tools the next time its tool list is refreshed (wiki: `ProductDocs/15-Capabilities.md § Connector detail view`, Refresh Tools control) — no platform-side registration step, no new credential, no new Code Project option (the repo already exists in that field).
- Rollback: revert the deploy. Since the change is purely additive (no existing tool touched, no schema, no migration), rollback is a plain redeploy of the prior image — the 6 tools disappear from the tool list, nothing else is affected.

### Test strategy

- Unit (mocked upstream, `tests/conftest.py`'s `httpx.MockTransport` fixture): one test per tool asserting (a) the exact cmdlet name and parameter dict sent, (b) field projection on the output, (c) the `not_found` envelope when the upstream returns an unresolved-recipient error, (d) `NO_CREDENTIALS` when no credentials are in context — same four assertions the existing tools already have coverage for (`tests/test_tool_calls.py`).
- Snapshot (`tests/test_tools.py`): extend `EXPECTED_TOOLS`, `_READ_ONLY`, `_DESTRUCTIVE`; this is also the regression guard that nothing existing broke (`assert names == set(EXPECTED_TOOLS)` fails closed on any accidental rename).
- No-tenant e2e (`tests/mock_e2e/`): extend `FIXTURES` with the 6 new cmdlets so `run_e2e.py` continues to exercise the full tool set against a mocked Entra + Exchange admin endpoint, verifying the real container (not just the Python function) end to end.
- Regression surface: the 7 existing tools are untouched code — the main regression risk is `server.py`'s registration order/`instructions` edit and `test_tools.py`'s snapshot assertions, both mechanical and caught immediately by the existing test suite (`uv run pytest`).
- Manual verification against a real tenant is out of scope for this design/dev cycle (no EXO tenant is reachable from this pipeline); the self-test gate for this ticket is the full `uv run pytest` + `uv run ruff check` suite, consistent with how the 7 existing tools were verified (per `git log`, `d7a85a7` and its predecessors ship without a real-tenant test step either).

### Effort & breakdown

- 1–2 person-days. Lower end if the field-projection assumption (Open Questions, SELF filtering) needs no back-and-forth; upper end if `document/vendor-mcp-development-sop.md` review (in `mcp-service-gateway`, out of this repo) surfaces a convention this design missed.
- Single sub-task is reasonable — all 6 tools share one module, one server.py edit, one README edit, and one test pass; splitting further would create artificial partial-PR states (e.g. "4 of 6 tools" is not independently valuable to the reporter, who needs all 6 for the Rewst flow to be replaceable).

### Risks & dependencies

- **Risk**: the exact property names `Get-MailboxPermission`/`Get-RecipientPermission` return (used for field projection, §4) are taken from Microsoft's documented cmdlet reference, not verified against a live tenant from this design flow. Mitigation: already covered by Test strategy — unit tests pin the exact projected shape against a controllable mock, so a wrong field name fails fast in CI rather than silently dropping data in production.
- **Risk**: `Add-MailboxPermission`/`Add-RecipientPermission` on an already-granted trustee, and `Remove-*` on a not-granted trustee, surface as whatever generic error text Exchange returns for that case — not pre-classified by `_NOT_FOUND_MARKERS` today. Mitigation: this falls through to the existing default classification (`invalid_argument`, non-retryable) via `_classify()` (`api_client.py:99-103`), which is a safe, non-misleading default; no code change required for v1, and the dev leg can add a specific marker if the real error text diverges materially (small, isolated follow-up, not a blocker to this ticket).
