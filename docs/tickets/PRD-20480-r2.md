## Tech design

### Conclusion

Five fixes, split two ways: D1–D4 are entirely inside `exchange_online_mcp` (the tech design's own documented fallback, now actually implemented); D5 is entirely inside `ms-graph-mcp` (a one-line UPN-resolution gap plus an error-shape inconsistency). None require a new scope, a schema change, or a cross-repo dependency — all four are additive/corrective changes to the same two tools (plus `exo_get_mailbox`) touched in the original round.

### Where the current implementation lives

- `exchange_online_mcp/src/exo_mcp/tools/permissions.py` — `exo_add_sendonbehalf_permission` (D1, D2, D3 read-back)
- `exchange_online_mcp/src/exo_mcp/tools/mailbox.py` — `exo_add_email_alias` (D1, D2, D3 read-back, D4); `exo_get_mailbox`'s `_MAILBOX_FIELDS` (D3 projection); new `_invalid_alias_prefix` helper (D4)
- `exchange_online_mcp/src/exo_mcp/tools/_common.py` — new `contains_case_insensitive` helper, shared by both write tools for the case-insensitive merge/dedup D1 and D2 need
- `ms-graph-mcp/src/graph_mcp/tools/groups.py` — `graph_add_group_owner` (D5); mirrors the existing UPN-resolution pattern already used by `graph_list_owned_groups` (`groups.py:264-267` pre-fix) rather than inventing a new one

### Option analysis

| Item | Option | Verdict |
|---|---|---|
| D1 wire format | Keep `{"Add": [...]}`, retry/backoff on "Invalid Operation" | Rejected — the error is deterministic (wrong shape), not transient; retrying would just fail the same way every time. |
| D1 wire format | Read-merge-write the full list (the fallback the original tech design already specified) | Accepted — exactly the documented fallback; the "not race-safe against a concurrent caller" risk flagged in the original Risks section is accepted as-is (same identity, low-traffic object, same class of risk `exo_set_mailbox_forwarding` already carries for its own read-before-write). |
| D2 validation | Let Exchange's own write-time rejection distinguish the error cases | Rejected — this is what the pre-fix code did, and it is exactly what Minnie's comment identified as broken: "a delegate that does not exist, an alias already used by another recipient, and a rejected format all return the same 'Invalid Operation'". |
| D2 validation | Precondition `Get-Recipient` read per candidate value, before any write | Accepted — turns an opaque write-time 400 into a specific, attributable result (`invalid` / `in_use_by_other`) using data Exchange itself returns, and lets the aliases loop continue past one bad address instead of aborting the whole call. |
| D4 prefix handling | Keep accepting any `":"`-containing prefix as "send as-is" (pre-fix behavior) | Rejected — this is the literal bug Minnie's comment describes: an `"SMTP:"`-prefixed address silently changes the primary, which "conflicts with 'existing primary is left untouched'". |
| D4 prefix handling | Allow only a bare address or an explicit lowercase `"smtp:"` prefix; reject everything else per-address | Accepted — matches the ticket's AC4 wording exactly ("existing primary address... left untouched") and fits the existing partial-success model from D2 (one bad address doesn't block the others). |
| D5 UPN handling | Document that `graph_add_group_owner` requires an object id, leave the tool as-is | Rejected — every other Graph tool in this repo's scope silently accepts a UPN; a documentation-only fix creates an inconsistent, surprising API. |
| D5 UPN handling | Resolve via `GET /users/{user_id}?$select=id` before `owners/$ref`, mirroring `graph_list_owned_groups` | Accepted — reuses an existing, already-tested pattern in the same file rather than inventing a new one. |

### Data & API contract

- `exo_add_sendonbehalf_permission(identity, delegate) -> str`: `{"identity", "delegate", "result": "added"|"already_present", "granted": true, "verified"?, "note"?}` on success; `{"error": {"code": "invalid_argument", ...}}` if `delegate` does not resolve via `Get-Recipient`; `{"error": {"code": "not_found", ...}}` if `identity` does not resolve. Cmdlets: `Get-Mailbox` → `Get-Recipient` → `Set-Mailbox -GrantSendOnBehalfTo <full list>` → `Get-Mailbox` (read-back).
- `exo_add_email_alias(identity, aliases) -> str`: `{"identity", "results": [{"address", "result": "added"|"already_present"|"in_use_by_other"|"invalid", "message"?}], "accepted": bool, "verified"?, "note"?}`. Cmdlets: `Get-Mailbox` → `Get-Recipient` per candidate address → `Set-Mailbox -EmailAddresses <full list>` (only if at least one address was new) → `Get-Mailbox` (read-back).
- `exo_get_mailbox(identity, include_statistics) -> str`: `mailbox` object gains `email_addresses: list[str]` and `grant_send_on_behalf_to: list[str]` (D3).
- `graph_add_group_owner(group_id, user_id) -> str`: unchanged success/already_owner shape (`{"group_id", "user_id", "status"}`); `user_id` now accepts a UPN or an object id; the returned `user_id` is always the *resolved* object id, not the caller's input, for consistency with what Graph itself now holds; failures are the standard envelope.

### Key flow / sequence

```
Agent -> exo-mcp: exo_add_email_alias(identity="shared@contoso.com", aliases=["old@contoso.com", "taken@contoso.com"])
exo-mcp -> Exchange: Get-Mailbox {Identity: "shared@contoso.com"}              -- current EmailAddresses
exo-mcp -> Exchange: Get-Recipient {Identity: "old@contoso.com"}                -- not found -> available
exo-mcp -> Exchange: Get-Recipient {Identity: "taken@contoso.com"}              -- resolves to a different mailbox -> in_use_by_other
exo-mcp -> Exchange: Set-Mailbox {Identity: "...", EmailAddresses: [<current> + "smtp:old@contoso.com"]}
exo-mcp -> Exchange: Get-Mailbox {Identity: "shared@contoso.com"}              -- read-back, sets verified
exo-mcp -> Agent: {results: [{address:"old@contoso.com", result:"added"}, {address:"taken@contoso.com", result:"in_use_by_other", message:"..."}], accepted: true, verified: ...}
```

### Non-functional

- Extra round trips: each write tool now does up to 1 (`Get-Mailbox`) + N (`Get-Recipient` per candidate, aliases only) + 1 (`Set-Mailbox`, skipped if nothing new) + 1 (`Get-Mailbox` read-back) calls, versus the prior single-call design. Accepted — correctness (distinguishing failure reasons, not corrupting the existing list) outweighs the added latency for what are deliberate, infrequent admin actions, not a hot path.
- Concurrency: the read-merge-write window is not race-safe against a second concurrent caller touching the same mailbox's same property — this was already flagged as an accepted risk in the original tech design's Option analysis and is unchanged here.
- Backward compatibility: both write tools' response shapes changed (`exo_add_sendonbehalf_permission` gained `result`, dropped bare `granted`-as-the-only-signal; `exo_add_email_alias` replaced `aliases_requested`/`accepted`-only with a per-address `results` array). This is a breaking response-shape change for any caller parsing the old shape — acceptable here because the old shape was reporting a success ("granted": true / "accepted": true) for calls that were actually failing on a real tenant (D1), so no caller could have been relying on it correctly.
- Multi-tenant isolation: unchanged — same per-request `client_factory()`/`GraphClient` wiring; no new tenant-scoping surface.

### Rollout & rollback

No new scope, no schema change, no new Exchange role. Both repos ship on next deploy with zero cross-repo dependency, same as the original round's `exchange_online_mcp` side. `graph_add_group_owner`'s pre-existing scope dependency (R1/R2 in Minnie's comment, Tech design §8 in `PRD-20480.md`) is unaffected by this fix — it is orthogonal (authorization vs. UPN-resolution). ### Risks & dependencies

- Risk (carried forward, unchanged): the read-merge-write window is not race-safe against a concurrent writer to the same mailbox property. Same risk class already accepted in the original round.
- Risk (new, D2/D4): the per-address precondition loop adds `Get-Recipient` calls proportional to the number of aliases in a single `exo_add_email_alias` call — no cap exists on `aliases` length; a caller passing an unreasonably large list would make an unreasonably large number of sequential calls. Not fixed in this round (out of scope — Minnie's comment did not flag it, and the ticket's own use case is "one or more" addresses for a single mailbox setup step, not bulk import); flagged for groom if bulk alias import becomes a real use case.
