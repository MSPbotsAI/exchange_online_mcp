## Current state (every claim carries path:line)

As of this round's base (`exchange_online_mcp@main` @ `fc0021c`, the merge commit that carried round 2's work into `main`):

- `exo_add_email_alias` (`src/exo_mcp/tools/mailbox.py:653-657` pre-fix) ran `recipients = await client.invoke("Get-Recipient", {"Identity": local})` inside a `try`/`except ExoError` that recorded **every** exception as `{"result": "invalid", "message": exc.message}`, then `continue`d — there was no branch for "the lookup itself says this address doesn't exist yet". Real Exchange answers `Get-Recipient -Identity <unused address>` with an HTTP 400 body containing `"couldn't be found"`, which `api_client.py:89-101`'s `_classify` already maps to `code="not_found"` — but `mailbox.py` never read `exc.code` before deciding the address was invalid. The INT symptom ("every new (unused) address is rejected as 'invalid'") is the direct, deterministic consequence: there is no code path in which a brand-new address could ever reach `results.append({"result": "added"})`.
- The round-2 unit tests (`tests/test_tool_calls.py::test_add_email_alias_adds_multiple_without_disturbing_existing`, `::test_add_email_alias_partial_success_writes_only_valid_addresses`) mocked a free address by setting `upstream.responses["Get-Recipient"] = []` — a **200 OK with an empty list**, which the conftest `Upstream.handler` (`tests/conftest.py:61-82`) only returns when no `cmdlet_errors` entry is set for that cmdlet. That is not what real Exchange sends for an unused identity (a 400 error, not a 200 empty list), so neither test ever exercised the `except ExoError` branch that actually has the bug. This is exactly the round-1 `#AC4`/TC-EXO-002 test-realism gap Minnie's comment identifies as the reason the bug shipped undetected.
- `exo_add_sendonbehalf_permission`'s already_present check (`src/exo_mcp/tools/permissions.py:171-175` pre-fix) compared the delegate string, `Get-Recipient`'s `Identity`, and its `PrimarySmtpAddress` against the mailbox's current `GrantSendOnBehalfTo` list, but never compared `ExternalDirectoryObjectId` — the field EXO actually stores in `GrantSendOnBehalfTo` once a `Set-Mailbox` write has replicated (confirmed on INT: `GrantSendOnBehalfTo` held a GUID like `c1dcd1cd-...`, not an email address). A repeat call inside the replication window (before the UPN/SMTP-keyed fast paths above would match anyway) falls through to the id-less comparison and reports `added` again.
- `_invalid_alias_prefix` (`src/exo_mcp/tools/mailbox.py:198-209` pre-fix) used one message for every rejected prefix, phrased around "would change the mailbox's primary address" — true only for `"SMTP:"`; Exchange does not treat `"x500:"` or other prefixes that way, so the message misdescribed the actual consequence for every non-`"SMTP:"` case.
- Neither write tool's docstring said anything about a repeat call landing inside an unfinished replication window — N3's root cause and N4's ask are the same caveat, one for `exo_add_sendonbehalf_permission` specifically (N3) and one for both tools generally (N4).

## Tech design

### Conclusion

Four fixes, all inside `exchange_online_mcp`, all localized to the two write tools already touched in rounds 1–2: one correctness fix (N1, the blocking one), one message-wording fix (N2), one robustness fix (N3), and one documentation addition (N4). ### Where the current implementation lives

- `src/exo_mcp/tools/mailbox.py` — `exo_add_email_alias`'s per-address `Get-Recipient` precondition loop (N1); `_invalid_alias_prefix` (N2); tool docstring (N4)
- `src/exo_mcp/tools/permissions.py` — `exo_add_sendonbehalf_permission`'s `already_present` check (N3); tool docstring (N3 caveat + N4)

### Option analysis

| Item | Option | Verdict |
|---|---|---|
| N1 | Treat every `Get-Recipient` `ExoError` as `invalid` (pre-fix behavior) | Rejected — this is the literal bug: a free address raises the same exception type as a genuine failure, and both were being handled identically. |
| N1 | Branch on `exc.code == "not_found"`, treat it the same as an empty `recipients` list (address free); keep every other error code as `invalid` | Accepted — uses the signal `api_client.py` already classifies, no new error-code vocabulary; a different failure (e.g. a malformed identity, a rate limit) still correctly blocks that address as `invalid` rather than silently treating an unknown failure as "free". |
| N1 | Treat every `Get-Recipient` error as "address free" (always add) | Rejected — would silently write an alias when the precondition check genuinely could not be evaluated (e.g. a transient upstream fault), which is worse than today's over-cautious "invalid". |
| N2 | Keep one shared message for all rejected prefixes | Rejected — the "would change the primary address" claim is false for non-`SMTP:` prefixes, which is actively misleading to whoever reads the tool's error text. |
| N2 | Two messages: one naming the primary-address consequence for `"SMTP:"`, one for everything else | Accepted — matches what Exchange actually does; no behavior change, message-only. |
| N3 | Leave the already_present check as UPN/SMTP-only | Rejected — INT confirmed a repeat call inside the replication window reports `added` twice, which is the exact symptom the comment describes. |
| N3 | Also compare `Get-Recipient`'s `ExternalDirectoryObjectId` against the current `GrantSendOnBehalfTo` list | Accepted — matches what EXO actually stores post-replication; optional per the comment ("Fix (optional)"), implemented anyway since it is a small, localized, low-risk addition that closes a real gap rather than just documenting it. |
| N4 | No documentation change | Rejected — the comment explicitly asks for this note on both tools. |
| N4 | Add a one-line replication-window caveat to both write tools' descriptions | Accepted — directly what was asked; kept short to stay under this repo's `test_tools_list_snapshot` 500-char description ceiling (`tests/test_tools.py:69`), which both updated docstrings had to be re-trimmed against. |

### Change list

- `src/exo_mcp/tools/mailbox.py` [changed] — `exo_add_email_alias`'s alias loop: on `ExoError` from `Get-Recipient`, `exc.code == "not_found"` now sets `recipients = []` (falls through to the existing "no recipient found → add" path) instead of always recording `invalid`; `_invalid_alias_prefix` now returns a distinct message for `"SMTP:"` vs. any other prefix; tool docstring gains the N4 replication-wait note.
- `src/exo_mcp/tools/permissions.py` [changed] — `exo_add_sendonbehalf_permission`'s `already_present` check gains a fourth comparison against `Get-Recipient`'s `ExternalDirectoryObjectId`; tool docstring gains the N3 "repeat call may still report added" caveat and the N4 replication-wait note.
- `tests/test_tool_calls.py` [changed] — 2 existing tests (`test_add_email_alias_adds_multiple_without_disturbing_existing`, `test_add_email_alias_partial_success_writes_only_valid_addresses`) switched their "free address" mock from `upstream.responses["Get-Recipient"] = []` to `upstream.cmdlet_errors["Get-Recipient"] = NOT_FOUND_ERROR`, matching real Exchange's actual response; 1 message assertion added to `test_add_email_alias_rejects_uppercase_smtp_prefix`; 3 new tests (N1 regression + N1 guard + N2 message split assertion already folded into the existing prefix tests) plus 1 new test for N3.
- `docs/tickets/PRD-20480.ac.json` [changed] — 5 new entries, TC-EXO-014 through TC-EXO-018 (N1, N2, N3, N4, and R1-R3-as-not-actioned respectively).

### Data & API contract

No response-shape change. `exo_add_email_alias`'s `results[].result` can now actually be `"added"` for a brand-new address (previously unreachable in practice due to N1); `message` text for `invalid` results differs per-prefix (N2). `exo_add_sendonbehalf_permission`'s `already_present` result is now reachable via one more input shape (object-id-only match, N3) with no new fields.

### Key flow / sequence

```
Agent -> exo-mcp: exo_add_email_alias(identity="alice@contoso.com", aliases=["new@contoso.com"])
exo-mcp -> Exchange: Get-Mailbox {Identity: "alice@contoso.com"}            -- current EmailAddresses
exo-mcp -> Exchange: Get-Recipient {Identity: "new@contoso.com"}            -- 400 "couldn't be found" -> ExoError(code=not_found)
exo-mcp (N1 fix): code == "not_found" -> treat as recipients=[] -> address is free -> queue "smtp:new@contoso.com"
exo-mcp -> Exchange: Set-Mailbox {Identity: "...", EmailAddresses: [<current> + "smtp:new@contoso.com"]}
exo-mcp -> Exchange: Get-Mailbox {Identity: "alice@contoso.com"}            -- read-back, sets verified
exo-mcp -> Agent: {results: [{address:"new@contoso.com", result:"added"}], accepted: true, verified: ...}
```

### Effort & breakdown

0.25 person-day — one blocking logic fix plus three small, independently low-risk follow-ups, all in two files already modified in prior rounds.

### Risks & dependencies

- Risk (unchanged, carried forward from round 2): the read-merge-write window for both write tools is not race-safe against a second concurrent caller touching the same mailbox's same property. N4's new documentation note is exactly this caveat made explicit to callers; it does not change the underlying risk.
- Risk (N1, accepted): `exc.code == "not_found"` is derived from `api_client.py`'s text-marker-based `_classify` (`"couldn't be found"` etc., `api_client.py:89-96`), which is itself pattern-matching on Exchange's English error text. If Exchange ever changes that wording or the tenant runs in a non-English locale producing different error text, this classification — and therefore N1's fix — could silently stop working (classified as `invalid_argument` instead of `not_found`, reverting to the pre-fix behavior for that tenant). This is a pre-existing risk in `_classify`, not newly introduced, but N1 is now one more caller that depends on it.
- No cross-repo dependency introduced.
