## Requirement understanding

One line: the reporter wants 5 specific missing tools/parameters added to two existing MCPs — Microsoft Graph (ms-graph) and Exchange Online (exchange-online) — so that M365 onboarding/offboarding and mailbox/Teams-permission workflows can complete end-to-end without a human falling back to the M365/Exchange admin UI.

The five items, as literally specified by the reporter (tool name chosen by the reporter, where it is used, which MCP, required params):
1. `graph_create_tap` (ms-graph) — generate a one-time/limited-use Temporary Access Pass for a new hire (E6), sent only to the manager.
2. `exo_add_sendonbehalf_permission` (exchange-online) — grant "send on behalf" on a shared mailbox (E5).
3. `exo_add_email_alias` (exchange-online) — add one or more alias/old addresses to a mailbox (E5, form question 14).
4. `graph_add_group_owner` (ms-graph) — set a group/Teams owner, gated on prior approval that happens outside this tool (E5).
5. `preferred_language` parameter on `graph_create_user` / `graph_update_user` — set new-hire UI language, e.g. `fr-CA` / `en-CA` (E2/E3).

Duplicate check already done by the reporter against PRD-20422 ("[Feature] Graph offboarding transfer and sync") — reviewed and not a duplicate. Confirmed by reporter: "Q1 A, A". Reporter: Felix.Zhou@mspbots.ai, filed 2026-10-14 (UTC+8), via Teams.

## Product design

### Goals / Non-goals

Goals:
- Add exactly the 5 tools/parameters the reporter listed, in the 2 MCPs named, with the parameters named.
- Each new tool/parameter is usable by an agent (once connector-authorized, see Current state) to complete the corresponding onboarding/offboarding step without a human going into the M365 admin center or Exchange admin center.

Non-goals (explicitly out of scope for this ticket):
- No new MCP/connector. Both `ms-graph-mcp` and `exchange_online_mcp` already exist and are already connected on the platform.
- No "remove" counterpart for any of the 3 new write tools (`exo_add_sendonbehalf_permission`, `exo_add_email_alias`, `graph_add_group_owner`) — the ticket only asked for the "add" direction, matching the existing one-fixed-verb-per-tool convention in both repos (e.g. `exo_add_mailbox_permission` / `exo_remove_mailbox_permission` are separate tools; a future PRD would add the remove counterparts the same way).
- No approval-workflow UI for group/Teams ownership. The ticket's own wording — "Teams only sets someone as owner after approval" — describes a human/SOP-level approval step that happens *before* an agent calls `graph_add_group_owner`; this ticket only builds the mechanical "set owner" action itself.
- No change to the platform-side OAuth scope grant or tenant re-consent flow (lives in a different repo, `MCP-Management-Service`'s `auth/oauth/vendors/msgraph.py` — not a Code Project option for this ticket and not under this ticket's repos). See Tech design §8 for why 2 of the 5 items depend on it.

### Acceptance criteria AC1..ACn

- AC1 (TAP): Given an agent has `ms-graph-mcp` connected and `graph_create_tap` authorized for it, When the agent calls `graph_create_tap` for a valid user with no optional parameters, Then the call returns a Temporary Access Pass code that is usable for sign-in exactly once within its lifetime window (one-time by default, matching the ticket's E6 "only sent to the manager" framing), and When the agent supplies `is_usable_once=false` and a `lifetime_minutes` value, Then the returned pass honors those settings.
- AC2 (TAP, error path): Given an invalid or non-existent `user_id`, When `graph_create_tap` is called, Then the tool returns a structured error (not a raw exception) identifying the user as not found.
- AC3 (SendOnBehalf): Given a shared mailbox and a delegate who does not yet have SendOnBehalf rights on it, When the agent calls `exo_add_sendonbehalf_permission(mailbox, delegate)`, Then the delegate is granted SendOnBehalf on that mailbox (confirmable via `exo_get_mailbox` once EXO has replicated the change).
- AC4 (Alias): Given a mailbox and one or more alias addresses that are not already in use elsewhere in the tenant, When the agent calls `exo_add_email_alias(mailbox, aliases=[...])` with one or multiple addresses in a single call, Then every valid address is added to the mailbox's address list and the mailbox's existing primary address and other aliases are left untouched.
- AC5 (Alias, error path): Given an alias address that is already assigned to a different recipient in the tenant, When `exo_add_email_alias` is called with it, Then the tool surfaces Exchange's rejection for that address rather than silently dropping it, and any other valid addresses in the same call are still evaluated (the overall result makes clear which addresses succeeded and which did not).
- AC6 (Group owner): Given a group or Team id and a user id who is not currently an owner, When the agent calls `graph_add_group_owner(group_id, user_id)`, Then that user becomes an owner of the group/Team, and When the same call is repeated for a user who is already an owner, Then the tool reports this as an already-satisfied state rather than a failure (mirrors the existing idempotent behavior of `graph_assign_groups` for group membership).
- AC7 (preferred_language): Given a valid BCP-47 language tag (e.g. `fr-CA`, `en-CA`), When it is passed to `graph_create_user` at creation or to `graph_update_user` on an existing user, Then the user's `preferredLanguage` attribute is set to that value, visible on a subsequent `graph_get_user` read.
- AC8 (permissions / multi-tenant, required by the quality line): Given a caller's token/credentials are scoped to tenant A (the existing per-request `client_factory()` / per-tenant app-registration wiring already used by every tool in both repos), When any of the 5 new tools/parameters is invoked, Then there is no code path or parameter that lets the caller target a different tenant's directory/mailbox — tenant isolation continues to be enforced entirely by the existing per-request credential wiring, not by any new logic this ticket adds.

### Open questions

- [已假设 / assumed] `graph_create_tap`'s default for `is_usable_once` is `true` (single use) when the caller omits it, matching the ticket's own framing of the E6 scenario (temporary code sent only to the manager, implying a tightly scoped one-time credential is the safer default). If this assumption is wrong, Tech design §4 only needs a one-line default-value change.
- [已假设 / assumed] None of the 3 new write tools gets a "remove" counterpart in this ticket (see Non-goals). If the reporter actually wants remove/undo capability too, that is new scope and should go through groom as a follow-up, not be added here silently.
- [不阻塞 / non-blocking] The exact Exchange error text returned when an alias address is already taken, or when a `GrantSendOnBehalfTo`/`EmailAddresses` "Add" is attempted against a value that is already present, is not yet confirmed against a real tenant (none of this is in the ticket or in the repo's existing code/tests) — Tech design §9 flags the specific test cases that need a real-tenant run to pin this down; it does not block writing or shipping the tools, only the exact wording of the structured error for that one edge case.
- [需人工 / needs a human, non-blocking for design but blocking for go-live of 2 of the 5 items] `graph_create_tap` and `graph_add_group_owner` need two Graph permission scopes (`UserAuthenticationMethod.ReadWrite.All`, `Group.ReadWrite.All`) that are not currently requested by the platform's shared Entra app registration (see Tech design §8). Granting this and getting already-connected tenants to re-consent is a `MCP-Management-Service` change, outside this ticket's two repos and outside this ticket's Code Project. This is fully specified (exact scope strings, exact mechanism), so it is not a design blocker — it is a sequencing dependency to flag at rollout/groom time.

#### Change list

- `src/graph_mcp/tools/users.py` [改] — add optional `preferred_language: str | None = None` parameter to `graph_create_user` and `graph_update_user`; when provided, set `body["preferredLanguage"] = preferred_language` (same `if x is not None` pattern already used for every other optional field in both functions).
- `src/graph_mcp/tools/users.py` [改] — add new tool `graph_create_tap(user_id, start_date_time: str | None = None, lifetime_minutes: int | None = None, is_usable_once: bool = True) -> str`, placed after `graph_list_auth_methods`. Body: `POST /users/{user_id}/authentication/temporaryAccessPassMethods` with `{startDateTime, lifetimeInMinutes, isUsableOnce}` (only non-`None` keys included, mirroring `GraphClient.invoke`-adjacent conventions already in this file). Annotate `idempotentHint=False` (Graph's own doc: a second call invalidates the first pass) and `readOnlyHint=False`.
- `src/graph_mcp/tools/groups.py` [改] — add new tool `graph_add_group_owner(group_id, user_id) -> str`, placed after `graph_assign_groups`. Body: `POST /groups/{group_id}/owners/$ref` with `{"@odata.id": _DIRECTORY_OBJECT_URL.format(user_id=user_id)}`; on `GraphError` with `status_code == 400` and an "already exist"/already-an-owner message, return `{"status": "already_owner"}` (mirror `graph_assign_groups`'s existing 400-handling at `groups.py:57-59`), matching AC6.

#### Data & API contract

- `graph_create_tap(user_id: str, start_date_time: str | None, lifetime_minutes: int | None, is_usable_once: bool = True) -> str` (JSON):
  - Request: `POST /users/{user_id}/authentication/temporaryAccessPassMethods` body `{"startDateTime": <iso8601>?, "lifetimeInMinutes": <int 10..43200>?, "isUsableOnce": <bool>?}`.
  - Response (success, 201): echo `{"user_id", "temporary_access_pass", "lifetime_minutes", "is_usable_once", "is_usable", "method_usability_reason"}` — field names taken directly from Graph's `temporaryAccessPassAuthenticationMethod` response.
  - Errors: `GraphError` passthrough — 403 if the scope is missing or the tenant has not re-consented (see §8), 404 if `user_id` does not resolve.
  - Security note: `temporary_access_pass` is a one-time sign-in secret. Graph's API contract requires returning it (there is no way to fetch it again later), so the MCP has no choice but to include it in the tool response — same exposure class as any other MCP tool result, no new logging sink is added, and no new code path persists it.
- `graph_add_group_owner(group_id: str, user_id: str) -> str` (JSON): `{"group_id", "user_id", "status": "added" | "already_owner" | "error", "detail"?}`. Request: `POST /groups/{group_id}/owners/$ref` body `{"@odata.id": "https://graph.microsoft.com/v1.0/directoryObjects/{user_id}"}`. Graph returns `204 No Content` on success (no body), matching the existing members/$ref call's handling style.
- `preferred_language` — no new endpoint; appended to the existing `graph_create_user`/`graph_update_user` request bodies as `"preferredLanguage": "<BCP-47 tag>"`.

#### Key flow / sequence

```
Agent -> graph-mcp: graph_create_tap(user_id="...", is_usable_once=true)
graph-mcp -> Graph API: POST /users/{id}/authentication/temporaryAccessPassMethods
Graph API -> graph-mcp: 201 { temporaryAccessPass: "...", isUsable: false, methodUsabilityReason: "NotYetValid" (if startDateTime in future) }
graph-mcp -> Agent: { temporary_access_pass: "...", ... }
Agent -> (SOP-level) hand the pass to the user's manager only
```

#### Non-functional

- Idempotency/concurrency: `graph_add_group_owner` is idempotent by design (already-owner → `already_owner`, not an error), mirroring `graph_assign_groups`. `graph_create_tap` is explicitly **not** idempotent — Graph replaces any existing TAP on a second call — so it is annotated `idempotentHint=False` and the docstring says so, matching how `graph_create_user`'s password-handling already warns about one-shot semantics elsewhere in this file.
- Performance: both are single synchronous Graph calls, no pagination, no new perf surface.
- Security: see the TAP secret-exposure note in §5 above — this is the first *write* tool in this repo whose success response must carry a secret value (every other write tool either echoes non-secret state or deliberately omits the secret, e.g. `graph_create_user` never echoes the password). Flagged as a risk in §11, not a blocker — Graph's contract gives no alternative.
- Multi-tenant isolation: unchanged. Both new tools and the new parameter go through the same per-request `client_factory()` wiring every existing tool uses; no new tenant-scoping surface is introduced (AC8).
- Observability: existing `GraphError.to_envelope()` / logging conventions apply unchanged; no new logging needed.

#### Rollout & rollback

- No DB, no feature flag (this server is stateless). Rollout = deploy the new image.
- `preferred_language` and both profile reads are immediately usable on deploy — no new scope needed (`User.ReadWrite.All` already covers it).
- `graph_create_tap` and `graph_add_group_owner` additionally require, in this order: (1) land this PR and deploy, (2) `MCP-Management-Service`'s `auth/oauth/vendors/msgraph.py` (different repo) adds `UserAuthenticationMethod.ReadWrite.All` + `Group.ReadWrite.All` to the requested delegated/application scope set, (3) every tenant that already authorized the Microsoft Graph connector must re-authorize before these two tools stop returning 403 for them — this exact sequencing already happened for `Mail.Read` (PRD-19103) and `Calendars.ReadWrite` (PRD-18631) per this repo's own README, so it is a known, repeatable process, not a new risk class.
- Rollback: revert the deploy; no data migration to undo either way.

#### Test strategy

- Unit (existing pattern, `tests/test_tools.py`): extend `EXPECTED_TOOLS`; add mocked-HTTP-level call tests for `graph_create_tap` (success + 403-looks-like-missing-scope) and `graph_add_group_owner` (success + 400-already-owner), mirroring the existing `graph_assign_groups` 400-handling test.
- No E2E/mock-upstream harness exists in this repo beyond the mocked `tests/test_tools.py` style (confirmed: `tests/` only has `test_middleware.py` and `test_tools.py`).
- Manual, real-tenant verification needed for (cannot be scripted in this repo, flagged rather than silently skipped): the actual 403 error text before vs. after tenant re-consent (same open question class as the already-documented Mail.Read/Calendars rollouts in this README); the actual Graph error text/status for "user is already an owner" on `/groups/{id}/owners/$ref` (unconfirmed — `graph_assign_groups`'s own 400-text match had to be pinned down the same way).
- Regression risk: none on existing tools — all three changes are additive (new functions, or a new optional parameter appended at the end of an existing signature).

#### Effort & breakdown

0.5–1 person-day for this repo's three changes (all three are small and closely pattern-matched to existing code). The cross-repo scope-grant + tenant-re-consent dependency (§8) is not estimable by this repo's owner alone — it belongs to the platform/`MCP-Management-Service` team and tenant admins, and is a sequencing dependency rather than additional work on this repo.

#### Risks & dependencies

- Dependency: `MCP-Management-Service`'s `auth/oauth/vendors/msgraph.py` scope grant + per-tenant re-consent (see Rollout). Not in this ticket's Code Project, not actionable by this ticket's implementer alone.
- Risk: TAP secret exposure in the tool's own success response (see Non-functional) — mitigated at the SOP/agent-usage level (the ticket's own framing already says "only sent to the manager"), not by new code in this repo.
- Assumption carried from Open questions: `graph_add_group_owner` is not special-cased for Teams vs. plain M365 groups — Microsoft Teams is backed by an M365 Group in Graph, so the same `/groups/{id}/owners/$ref` endpoint applies to both; if a real Teams-backed test reveals different behavior, this needs revisiting (flagged, not blocking).

#001 technical uncertainty (not a blocker, flagged for implementation): Exchange's REST-based remote-PowerShell wire format for a multi-valued `Add`/`Remove` cmdlet parameter (PowerShell's `@{Add=...}` hashtable syntax for `-GrantSendOnBehalfTo` and `-EmailAddresses`) has not been exercised anywhere yet in this repo — every existing `Set-Mailbox` call here (`exo_set_mailbox_hidden`, `exo_set_mailbox_forwarding`) sets a scalar property, never a multi-valued Add/Remove one. `ExoClient.invoke` (`api_client.py:235-244`) passes parameters through as a plain JSON dict with no special-casing, so the natural first attempt is `{"GrantSendOnBehalfTo": {"Add": [delegate]}}` / `{"EmailAddresses": {"Add": ["smtp:" + a for a in aliases]}}` — if the real REST endpoint rejects this shape, Option analysis below gives the fallback (read-merge-write the full array instead).

#### Option analysis

| Item | Option | Verdict |
|---|---|---|
| SendOnBehalf | `Set-Mailbox -GrantSendOnBehalfTo @{Add=<delegate>}` (additive) | Preferred — matches the ticket's single-delegate "add" semantics and this repo's one-fixed-verb-per-tool convention. **Fallback if the Add-hashtable wire form is rejected**: read the mailbox's current `GrantSendOnBehalfTo` list via `exo_get_mailbox`, append the delegate, and `Set-Mailbox -GrantSendOnBehalfTo <full list>` — functionally equivalent but not race-safe against a concurrent caller; use only if the additive form does not work. |

| Alias | `Set-Mailbox -EmailAddresses @{Add="smtp:<addr>"}` (additive, multi-address in one call) | Preferred — matches the ticket's explicit ask to retain multiple old/alias addresses. Same fallback contingency as SendOnBehalf if the wire form is rejected. |

#### Data & API contract

#### Key flow / sequence

```
Agent -> exo-mcp: exo_add_email_alias(identity="shared@contoso.com", aliases=["old-name@contoso.com"])

exo-mcp -> Agent: { identity, aliases_requested, accepted: true, verified: false, note: "replicates within a few minutes; confirm with exo_get_mailbox" }
```

#### Non-functional

- Idempotency: both are additive "Add" operations on multi-valued properties — Exchange's typical behavior is to no-op a duplicate Add rather than error (unlike `Add-MailboxPermission`, which errors on a duplicate grant). This needs confirming against a real tenant (flagged, not assumed as fact).
- Replication delay: identical caveat to the two existing `Set-Mailbox` tools — both new tools return `verified: false` and point at `exo_get_mailbox`, exactly mirroring `mailbox.py:205-210`'s existing wording.
- Security: SendOnBehalf is a trust-delegation action, same risk class as the already-shipped `exo_add_mailbox_permission` (both grant one user the ability to act through another mailbox) — no new risk category introduced, same tool annotation style applies.
- Multi-tenant isolation: unchanged — identical per-tenant app-registration + `Recipient Management` role boundary as every existing tool (AC8).
- Observability: existing `ExoError`/logging conventions apply unchanged.
